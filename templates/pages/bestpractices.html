Best Practices
Do's and don'ts for notebooks, jobs, pipelines and code conventions
Notebooks
DEVELOPMENT
Do
  • → Use a single responsibility per notebook — one notebook = one logical task
  • → Parameterize notebooks with dbutils.widgets instead of hard-coded values
  • → Add a header cell with: author, date, purpose, and input/output tables
  • → Version-control all notebooks via Git integration (Repos)
  • → Use %run for shared utility notebooks instead of copy-pasting code
Don't
  • → Never hard-code secrets, passwords or connection strings in notebooks
  • → Don't use .collect() on large DataFrames — it pulls all data to the driver
  • → Avoid running production logic from All-Purpose clusters; use Job Clusters
  • → Don't leave exploratory / scratch cells in notebooks destined for jobs
  • → Never edit notebooks directly in Prod — always deploy via CI/CD
Delta Tables & Storage
DATA LAYER
Do
  • → Partition tables by date columns (e.g. year/month/day) for large tables
  • → Run OPTIMIZE + ZORDER weekly on high-query Gold tables
  • → Enable delta.enableChangeDataFeed on tables used in streaming downstream
  • → Use MERGE INTO (upsert) for incremental loads instead of full overwrites
Don't
  • → Don't over-partition — avoid columns with very low cardinality (e.g. boolean)
  • → Don't skip VACUUM — old file accumulation increases storage costs significantly
  • → Avoid writing many small files — use repartition() before writing
  • → Never drop or overwrite a Gold table without peer review approval
Jobs & Orchestration
WORKFLOWS
Do
  • → Always use Job Clusters (not All-Purpose) for scheduled production jobs
  • → Set retry policies (at least 2 retries) and alerting on all production jobs
  • → Use task dependencies to model pipeline DAGs within a single Workflow
  • → Deploy all jobs via Databricks Asset Bundles (DAB) — no manual UI creation in Prod
Don't
  • → Don't schedule jobs without at least one email/Slack alert on failure
  • → Avoid using time-based cron if an event-trigger is possible and more reliable
  • → Don't create jobs without a runbook documenting manual recovery steps
